1. System Architecture & CAT 1 Design

The KCAU Smart Dining System is engineered according to Continuous Assessment Test 1 (CAT 1) requirements. It transitions client-only logic to a high-performance, modular Java backend that connects directly to a persistent SQLite relational database while delivering three interconnected portal experiences.

+-------------------------------------------------------------------------------------------------------+ | THREE CONNECTED USER INTERFACES | | 1. STUDENT PORTAL : Browse Menu from Java, Tray Cart, Simulated M-Pesa STK, Receipt & Track | | 2. DINING STAFF PORTAL : Live Kitchen Queue, Status Controls (PREPARING, READY, COLLECTED), Ledger| | 3. ADMINISTRATOR PORTAL : Real-time Sales KPIs, Meal Availability Toggle, Add Dish, Role Control | +-------------------------------------------------------------------------------------------------------+ | REST JSON APIs over HTTP (Port 3000) v +-------------------------------------------------------------------------------------------------------+ | MODULAR JAVA APPLICATION ENGINE | | - com.kcau.dining.Server : Virtual Thread HTTP Server (com.sun.net.httpserver) | | - com.kcau.dining.handler.* : UserHandler, MenuHandler, OrderHandler, PaymentHandler, ReportHandler | | - com.kcau.dining.service.* : UserService, MenuService, OrderService, PaymentService, ReportService | | - com.kcau.dining.model.* : User, MenuItem, Order, OrderItem, Payment | +-------------------------------------------------------------------------------------------------------+ | JDBC Connectivity v +-------------------------------------------------------------------------------------------------------+ | RELATIONAL SQLITE DATABASE | | - data/dining.db : Foreign-keyed tables (users, menu_items, orders, order_items, payments) | | - DatabaseInitializer.java : Automated DDL table creation and initial seed data | +-------------------------------------------------------------------------------------------------------+
Dual Deployment Model: When executed locally, the application runs on the modular Java backend with SQLite persistence on http://localhost:3000. When deployed to Vercel (https://kca-cafeteria.vercel.app), the frontend leverages the resilient client-side LocalDB layer so the interactive demo works seamlessly in serverless edge environments.

Modular Java Architecture

Strictly partitioned into Model, Database, Service, Handler, and Server packages with virtual thread concurrency.

ACID Relational Storage

SQLite persistence ensures all accounts, food catalogs, meal tickets, and payment ledger entries survive restarts.

Role-Based Access Control

Three explicit user roles: STUDENT, STAFF, and ADMIN with cryptographic JWT authentication.

Dynamic Availability & Analytics

Sold out items toggle dynamically; Java calculates real-time revenue and dish popularity rankings.

3.2 Backend Service Implementation Details

  • OrderService (Transactional ACID Order Creation): 
    // Atomic Order & OrderItem insertion within a single SQLite transaction
conn.setAutoCommit(false);
try (PreparedStatement orderStmt = conn.prepareStatement(insertOrderSql);
     PreparedStatement itemStmt = conn.prepareStatement(insertItemSql)) {
    // 1. Insert master order row
    orderStmt.setString(1, order.getOrderId());
    orderStmt.setString(2, order.getUserId());
    orderStmt.setDouble(4, order.getTotalAmount());
    orderStmt.executeUpdate();

    // 2. Batch insert individual order items
    for (OrderItem item : order.getItems()) {
        itemStmt.setString(1, order.getOrderId());
        itemStmt.setString(2, item.getFoodName());
        itemStmt.setInt(3, item.getQuantity());
        itemStmt.setDouble(4, item.getUnitPrice());
        itemStmt.addBatch();
    }
    itemStmt.executeBatch();
    conn.commit(); // Fully persisted atomically
}
  • ReportService (SQL Data Aggregation): Calculates real-time total revenue, order count by status, average ticket value, and dishes ranked by quantity sold: 
    SELECT oi.food_name, SUM(oi.quantity) AS qty, SUM(oi.quantity * oi.unit_price) AS rev
FROM order_items oi JOIN orders o ON oi.order_id = o.order_id
WHERE o.order_status != 'CANCELLED'
GROUP BY oi.food_name ORDER BY qty DESC;
  • MenuService (Dynamic Availability Control): Toggles dish availability via UPDATE menu_items SET available = ? WHERE id = ?, immediately affecting student menu rendering.

4. REST API Endpoint Reference

All HTTP endpoints exchange standard JSON payloads and support Cross-Origin Resource Sharing (CORS):

Method URI Endpoint Request Body Functionality & Status
POST /api/signup { name, studentId, password, role } Validates fields, creates user in SQLite with PBKDF2 hash. Returns 201 Created.
POST /api/login { studentId, password } Authenticates credentials, returns signed JWT token with role. Returns 200 OK.
GET /api/me Bearer <token> Header Validates active JWT session and returns user identity. Returns 200 OK.
GET /api/users None (Admin) Returns list of all registered accounts and current roles. Returns 200 OK.
PUT /api/users/role { userId, role } Promotes or updates account role to student, staff, or admin. Returns 200 OK.
GET /api/menu Optional ?category=... Returns complete menu catalog loaded from SQLite with availability flags. Returns 200 OK.
POST /api/menu { name, category, price, desc, image } Adds a new dish to the cafeteria database. Returns 201 Created.
PUT /api/menu/availability { foodId, available: boolean } Toggles dish status between In Stock and Sold Out in real time. Returns 200 OK.
POST /api/orders { userId, customerName, totalAmount, items } Creates order ticket in SQLite with line items in an atomic transaction. Returns 201 Created.
GET /api/orders None (Staff/Admin) Retrieves all kitchen queue orders with item breakdowns. Returns 200 OK.
PUT /api/orders/status { orderId, status } Transitions order status (PREPARING, READY, COLLECTED). Returns 200 OK.
POST /api/payments { orderId, method, amount, reference, status } Records simulated payment transaction in payments table. Returns 201 Created.
GET /api/payments None (Staff/Admin) Returns full cafeteria transaction ledger. Returns 200 OK.
GET /api/reports/summary None (Admin) Calculates revenue, order counts by status, and registered user total. Returns 200 OK.
GET /api/reports/sales None (Admin) Returns dishes ranked by servings sold and total revenue earned. Returns 200 OK.

5. Frontend Architecture & Three Connected Interfaces

The frontend is structured as a reactive Single Page Application (SPA) across public/index.html, public/style.css, and public/app.js:

5.1 The Three Connected Portals

  • 1. Student Portal (#student-menu):
    • Dishes loaded dynamically from Java SQLite backend (GET /api/menu).
    • Displays category filter pills (Breakfast, Lunch, Drinks, Fruits) and live search input.
    • Items marked available = false render with a red SOLD OUT badge and disabled Add button.
    • Floating Cart Dock tracks quantity and total price.
    • Checkout modal supports simulated M-Pesa STK push, Airtel Money, Card, and Cash at Counter.
    • Digital receipt generates Order ID and reference code.
    • Active Order Tracking banner polls status changes from the kitchen.
  • 2. Dining Staff Portal (#kitchen-dashboard):
    • Live Orders Queue displaying order cards with customer name, items list, and timestamps.
    • Filter pills: All, Pending, Preparing, Ready, Collected.
    • Status progression buttons: Start Preparing 🍳 -> Mark Ready 🔔 -> Mark Collected ✓.
    • Payment ledger tab displays transaction references and amounts.
    • Auto-polls the Java backend every 4 seconds.
  • 3. Administrator Portal (#admin-dashboard):
    • KPI summary cards: Total Revenue, Total Orders, Active in Kitchen, Registered Users.
    • Tab 1: Sales analytics with top-selling dishes and recent orders.
    • Tab 2: Meal catalog management with live Availability Toggle button and Add Dish modal.
    • Tab 3: User accounts table with role modification dropdown (Student / Staff / Admin).
